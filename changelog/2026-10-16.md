## [x] Feature: move image / segment rows up and down in the Config Editor

- **Status:** done (unit-tested decision rule `move_target`; the Qt part needs a manual check in Slicer)
- **Why:** the order of `images[]` and `segmentation.segments[]` matters (load order, layer order, segment order in the
  segmentation), but rows can only be appended or removed, so fixing the order means deleting and re-adding rows.
- **Plan:**
  1. Add **Move up** / **Move down** buttons next to *Remove selected* on the Images and Segmentation tabs.
  2. The buttons act on the selected (current) row and keep it selected after the move.
  3. *Move up* is disabled when the first row is selected, *Move down* when the last row is selected, and both when
     nothing is selected or the table is empty. The state is refreshed on every selection change, add, remove,
     populate and clear.
  4. Moving swaps the row with its neighbour. Rows carry widgets (combos) and parallel lists (`_image_advanced`,
     `_segment_colors`), so the move is done by snapshotting every row as a dict, swapping two entries and rebuilding
     the table - the same code path that loads a config, so nothing can get out of step. Unnamed rows are kept.
  5. After an image move the Volume Rendering table and the Reference image dropdowns are re-synced (image order).
  6. Shared, Qt-free helper `move_target(row, delta, count)` in `gui/config_editor/helpers.py` (unit-tested) decides
     both the target row and whether a button is enabled.
  7. Docs: `docs/config-editor.md`, the Config Editor cheat sheet, `CHANGELOG.md`.
- **Manual check in Slicer:** select a middle row -> both buttons enabled; first row -> Up disabled; last row -> Down
  disabled; move, save, reopen -> order kept, widgets/advanced values/colors stayed with their rows.

## [x] Bugfix: Segment editor `overwrite_mode` "none" was not stored

- **Status:** done (unit tests pass; the Qt/Slicer part needs a manual check in Slicer)
- **Problem:** `none` is a valid overwrite mode (= allow overlap), but the Config Editor treated it as "nothing set":
  a config with only `overwrite_mode: "none"` was not saved, and the Segment editor block was dropped on save.
- **Related bug found while checking:** when `overwrite_mode` was missing but e.g. a brush was configured,
  `configure_segment_editor_defaults` still forced `OverwriteNone` on the node (unset was indistinguishable from none).
- **Fix:**
  - the dropdown now has `(unset)` as its first, default entry (`OVERWRITE_CHOICES` in `definitions.py`);
  - `none` is written whenever it is chosen, `(unset)` omits the key;
  - `overwrite_value()` returns `None` for unset and the node's overwrite mode is only set when a value is configured.
- **Manual check in Slicer:** choose `none` only -> Save -> reopen: still `none` and `"segment_editor": {"overwrite_mode": "none"}`
  in the JSON; `(unset)` + a brush -> no `overwrite_mode` key and the Segment Editor's "Allow overlap" is not touched.

## [x] Bugfix: "Show 3D" shows nothing - `[VTK] Convert: Source representation scalar type is not a valid integer type`

- **Status:** fix written, **not verified in Slicer**. The cause is inferred from the VTK message, not reproduced.
- **Likely cause:** a segment's binary labelmap has a float/double voxel type - either a label image saved as float, or
  an empty placeholder created from a float reference volume (`CreateLabelVolumeFromVolume`). The conversion to a
  closed surface (Show 3D) needs an integer type.
- **Fix:** `ensure_integer_labelmap()` (`utils/segment_editor.py`) casts a non-integer label volume to short before
  it is imported as a segment; used for loaded label files and for empty placeholders (`study/specimen.py`). Loading a
  float label file logs an INFO line.
- **Not fixed:** a `segment.seg.nrrd` that was already saved with float segments keeps them. Remedy: close the specimen and
  use *Reset* (re-creates it), or re-save after the fix from fresh segments; otherwise tell me and I add a repair on load.
- **Manual check:** load a specimen with a float mask / float reference volume -> Show 3D works, no `Convert:` messages.

- **Checked against the Slicer 4.8 API docs (vtkMRMLSegmentEditorNode):** the mask-mode constants are `PaintAllowedEverywhere = 0`,
  `PaintAllowedInsideAllSegments`, `...InsideVisibleSegments`, `...OutsideAllSegments`, `...OutsideVisibleSegments`,
  `...InsideSingleSegment`; the setter is `SetMaskMode(int)` (+ `SetMaskSegmentID` for the single-segment mode). Our first
  names were therefore right for 4.8, yet Slicer 5.10 reported 'everywhere' unsupported - so 5.10 evidently spells them
  differently. The lookup now matches any `*Allowed<Suffix>` constant (note `PaintAllowedEverywhere` is 0, so the check is
  `is None`, never truthiness) and the warning still lists what the node has, to settle the 5.10 names from the log.

- **Root cause found (editable_area):** in current Slicer the constants are `vtkMRMLSegmentationNode.EditAllowedEverywhere`,
  `...InsideAllSegments`, `...InsideVisibleSegments`, `...OutsideAllSegments`, `...OutsideVisibleSegments`,
  `...InsideSingleSegment` (source: Slicer `vtkMRMLSegmentEditorNode.h`: `MaskMode` "uses vtkMRMLSegmentationNode::EditAllowed_..."),
  not on the segment editor node. `editable_area_value()` now searches `vtkMRMLSegmentationNode` first, then the editor node.
  Still to confirm in Slicer.

- **Fix (editable_area, Slicer 5.12 confirmed by the maintainer):** the `EditAllowed*` constants are not exposed as Python
  attributes, but `slicer.vtkMRMLSegmentationNode.ConvertMaskModeToString(0)` -> `'EditAllowedEverywhere'`, `(1)` ->
  `'EditAllowedInsideAllSegments'` work. `editable_area_value()` now finds the integer by asking for each mode's name
  instead of looking for attributes. `SetMaskMode(int)` on the editor node is still unconfirmed.

## [x] Segment Editor: changing the source volume keeps the background, the foreground follows

- **Status:** written, **not verified in Slicer** (layer behaviour cannot be run here).
- **Problem:** picking a source volume in the Segment Editor makes Slicer put it into the slice views' background and
  switch the foreground off, so the image the user was looking at disappeared.
- **Change:** `SourceVolumeLayerKeeper` (`utils/segment_editor.py`) remembers the layers shown right before the Segment
  Editor is set up for a specimen. When the source volume changes it queues (zero-delay timer, so Slicer finishes its own
  change first) a restore: background back to the remembered one, new source volume into the foreground (opacity as it
  was). If the source volume IS the remembered background (the usual reference image), the remembered foreground is put back.
  Stopped in `GenericSpecimen.close()`. Fixed rule, no new config option.
- **Limits:** the "kept" background is the one from the specimen load (config roles); a background the user changes by hand
  later is not tracked. Only active when the Segment Editor is activated for the specimen (a `segment_editor` block in the config).
- **Manual check:** load a specimen, open Segment Editor, switch the source volume -> background stays, the chosen image is
  the foreground; switch back to the reference image -> original foreground returns. If the layers still flip, the timer
  delay may need to be longer.

## [ ] Plan (future idea): per-segment foreground / background image

- **Status:** REJECTED by the maintainer on 2026-10-20 ("it would be annoying") - do not build. Replaced by a fixed rule: the first foreground image is the Segment Editor's source volume by default (see changelog/2026-10-20.md). Original idea kept below for the record.
- **Idea:** every segment definition can name an image to show as the slice views' **background** and one as the
  **foreground** while that segment is being edited. Both default to empty = do not touch the layers (today's behaviour).
- **Where it would be set:** in the segment definition (`segmentation.segments[]`), as two optional dropdowns filled from
  the image names of the Images tab (same mechanism as the *Reference image* dropdown, `(unset)` = empty). Proposed keys:
  `background_image` and `foreground_image`.
- **What happens:** when the segment becomes the one being edited (active segment in the Segment Editor), the module puts
  the named images into the background / foreground layer. The image's own settings from the Images tab are used -
  opacity, window/level, color table, interpolation (i.e. what `_apply_visual_props` / the role logic already apply on
  load), so nothing new has to be configured per segment.
- **Open questions:**
  1. The idea says "on the Images tab" - is it the Images tab that should hold the choice (e.g. a "used by segments"
     column), or the Segmentation tab's segments table with dropdowns fed from the Images tab? Current proposal: the latter.
  2. How is the active segment detected - observe the Segment Editor node's selected segment (`GetSelectedSegmentID`)
     and map it to the segment name. Needs a check in Slicer.
  3. Interaction with `SourceVolumeLayerKeeper` (2026-10-16, above): a per-segment setting should override the "kept"
     background / foreground while that segment is active, and the keeper's remembered layers become the fallback for
     segments with empty fields.
  4. Should it also apply the image's role-based extras (e.g. hide the other layers)? Probably not in a first version.
- **Would touch (when implemented):** `core/config_model.py` (SegmentConfig fields), `gui/config_editor/segmentation_tab.py`
  (two dropdown columns, refreshed with the Images tab like the reference-image dropdowns), `utils/segment_editor.py`
  (observer + layer switch), `docs/config-reference.md`, `docs/config-editor.md`, the cheat sheet, `CHANGELOG.md`; plus
  a test for the config parsing.
