### What MONAI Label's server side is (as read)
- A FastAPI app around a `MONAILabelApp` (infer / train / strategy / scoring tasks) and a **`Datastore`** interface. Methods:
  `list_images`, `get_image` / `get_image_uri`, `get_image_info`, `get_label` / `get_label_uri`, `get_label_info`,
  `get_labels_by_image_id`, `get_labeled_images(label_tag)`, `get_unlabeled_images(label_tag)`, `add_image`, `remove_image`,
  `save_label(image_id, label_filename, label_tag, label_info)`, `remove_label`, `update_image_info`, `update_label_info`, `datalist`,
  `get_dataset_archive`, `refresh`, `status`. Implementations: `LocalDatastore`, DICOMweb, XNAT, CVAT, DSA.
- **Data model of `LocalDatastore`** (`datastore_v2.json`): `objects: {image_id: {image: {ext, info}, labels: {tag: {ext, info}}}}` -
  i.e. **one image file per id**, any number of labels per id keyed by a **tag** (`original` = model output, `final` = submitted by a
  human); `info` is a free-form dict on both images and labels. Labels live in `labels/<tag>/`.
- **REST** (FastAPI, role-checked): `GET /datastore/` (everything), `PUT|GET|HEAD|DELETE /datastore/image`, `GET|PUT /datastore/image/info`,
  `PUT|GET|HEAD|DELETE /datastore/label`, `GET|PUT /datastore/label/info`, `GET /datastore/dataset` (ZIP),
  `POST /activelearning/{strategy}` (returns the next sample and stamps `strategy: {ts, client_id}` into the image info), plus
  `/info` (models, labels, strategies, config), `/infer`, `/batch_infer`, `/train`, `/scoring`, `/session`, `/login`.
- **Auth/roles:** optional (`MONAI_LABEL_AUTH_ENABLE`), Keycloak-based, roles user / annotator / reviewer / admin.
- **Concurrency:** no lock or lease was found in what was read. Several users are kept apart only by the active-learning strategies and
  the `client_id` / timestamp marks in the image info; a label save for a tag just replaces the file.
- **Config:** server settings from environment (`config.py`: app dir, studies dir, datastore kind/URL/credentials, auth) and the app's own
  labels/model configuration - nothing like a study description (names, paths, statuses, export).

### What MONAI Label's Slicer side is (as read)
- A scripted module `MONAILabel` (extension, category *Active Learning*; Slicer >= 5.0), settings under *Application Settings > MONAI Label*.
  It talks to the server with `MONAILabelClient` (plain HTTP: `info`, `next_sample`, `upload_image`, `save_label`, `download_label`,
  `infer`, `train_*`, `datastore`).
- Flow: connect (server URL, optional login) -> `info` (models, strategies, labels) -> **Next Sample** (run a strategy, download the
  image, load the volume, load the existing `original` label if any) -> edit in Slicer's Segment Editor / run an inference model
  (auto, DeepGrow, DeepEdit ...) -> **Submit Label** (export the segmentation as a labelmap `.nii.gz` or `.seg.nrrd` plus
  `label_info` = segment names / indexes, `save_label(image_id, label, tag)`).
- One volume per sample; segmentation/stats/workflow rules (names, paths, status, batch export) are not its business.

### How this module could use it (design)
1. **`StudySource` interface** in `study/` (the layer rule `core <- utils <- study <- gui` allows it), with `LocalStudySource` = today's
   behaviour (CSVs, folders, `safe_io`, lock file) and a remote implementation. `GenericSpecimen` / the GUI stop knowing where data comes
   from. Needed operations: list specimens, get a specimen's images (cached to a local folder), get / save the segmentation, get / set
   the status, claim / release a specimen, get the study config.
2. **Remote = our own thin server speaking a MONAI Label-compatible subset** (same endpoint names and `info` dicts where it makes
   sense: `/datastore`, `/datastore/image`, `/datastore/label`, `/info`) **plus** what MONAI Label lacks:
   - **several images per specimen**: either a custom `Datastore` whose image `info` carries sibling image ids and their *names* /
     roles, or one id per image with a naming convention (`<specimen>__<image name>`) - to be decided;
   - **the study config**: the server hands out the same `config.json` (names, patterns, roles, segments, batch export), so the client
     keeps applying it locally - the thing MONAI Label does not do;
   - **claim / lease** per specimen with a timeout (replaces the lock file), **versioned saves** (ETag / revision: a save on top of a
     newer version asks, like today's "database.csv changed on disk" question), **status** (0-3) kept server side.
3. **MONAI Label as an optional inference service behind that server**: its `infer` output becomes the pre-segmentation label map
   (what `source: "file"` segments already consume), and finished specimens' batch-export label maps can go back as `final` labels
   for training. This is the "ecosystem" loop of CLAUDE.md, not a merge of the two code bases.
4. **Plugin-like packaging:** the server and the remote source are optional; without them the module behaves exactly as now. No new
   options in the main GUI for the local mode.

## [ ] Plan (future idea): AI pre-segmentation jobs on top of the server (thin server + worker + MONAI Label)

- **Status:** planned only - nothing implemented. Builds on the section above; not before steps 1-4 of its order.
- **Goal:** run AI segmentation on the images of a specimen through a MONAI Label server and use the result as the pre-segmentation
  (`source: "file"` segments), with several images going to separate models, or helper segmentations being sent together with a given image.

### Three kinds of job
1. **Independent jobs** - one (model, image) pair each, e.g. the `t1` image into a liver model and the `pet` image into a tumour model. Run
   in any order or in parallel; each output is mapped to segments.
2. **Cascade** - a later job uses an earlier job's segmentation: the segmentation defines a region (bounding box + margin) and the next
   model sees only that crop (the result is pasted back into the full geometry). Works with models that know nothing about cascades.
3. **Image + helper segmentation together** - three ways, depending on the model:
   - pass the segmentation as the input label of the infer call (`label_in` in `MONAILabelClient.infer`; for models that take a
     starting label / guidance, e.g. DeepEdit-like ones);
   - stack image and segmentation into one multi-channel input prepared by our side (the model must have been trained for that, and a
     custom infer task is needed on the MONAI Label side);
   - the cascade above.

### Who does what
| Part | Does | Needs |
|---|---|---|
| **thin server** | serves specimens / images / config / status / claim / revisions; stores the jobs and their state (queued / running / done / failed); records provenance (model, model version, input images, time); saves a result as a new revision | FastAPI + small store, no GPU, no ML libraries |
| **worker** (separate process, optional) | prepares inputs (crop, stack channels, resample), calls MONAI Label, converts the result back into the specimen's geometry | SimpleITK or nibabel + numpy; only where cascade / multi-channel jobs are used |
| **MONAI Label server** (own host, GPU) | the actual inference (`/infer`, `/batch_infer`), models and their `/info` | PyTorch / MONAI, installed there only |

### Config sketch (not a decision) - same language as the rest of the config: images and segments by name
```
"auto_segmentation": [
  {"name": "liver_stage1", "model": "liver_seg",   "input": "image",        "image": "t1",
   "output": {"1": "liver"}},
  {"name": "liver_parts",  "model": "liver_parts", "input": "image+label",  "image": "t1", "label_from": ["liver"],
   "output": {"1": "liver_left_top", "2": "liver_right_top"}}
]
```
- `input` is declared **per model** (`image`, `image+label`, `multichannel`, `cascade`) and checked against the model's entry in the MONAI
  Label `/info` answer before the job starts; an unsupported combination is a clear message, not a failed inference.
- `output` maps the model's label values to segment names of `segmentation.segments[]` (names, never indexes, are what the study uses).
- A later job can refer to segments produced by an earlier one (`label_from`), which also defines the order of execution.

### Rules that follow from the project's principles
- **Never overwrite human work.** An AI result is a new revision with provenance; it is used as the starting segmentation only when the
  specimen has no human-saved segmentation. A human save is a newer revision on top; the AI revision stays.
- **No silent geometry changes.** Results are resampled back to the segmentation's reference geometry (`segmentation.reference_image`);
  a mismatch is reported, not guessed.
- **Failures are visible.** A failed or timed-out job shows in the job list with the reason; the specimen stays usable without it.
- **Optional all the way.** Without the server, the worker and a MONAI Label host the module behaves exactly as today.

### Order of work (after steps 1-4 of the server plan)
1. Job model + store + status API on the thin server (a job is a record; nothing runs yet).
2. Independent jobs: the server calls a MONAI Label `/infer`, saves the result as an AI revision with provenance, maps `output` to segments.
3. Per-model `input` declaration, checked against `/info`.
4. Worker + cascade (crop / paste back).
5. Image + helper segmentation (`label_in`; then multi-channel if a model needs it).
6. Training loop: finished specimens' label maps from the batch export go back to MONAI Label as `final` labels.
