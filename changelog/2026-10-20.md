## [x] Built-in colour maps: `gnuplot2` and `inferno`

- **Status:** written, **not verified in Slicer** (the colour table node recipe could not be run here).
- **Why:** an image should be shown with a matplotlib-like colour map (gnuplot2 or inferno); Slicer has no gnuplot2.
- **What:** `color_table: "gnuplot2"` / `"inferno"` in an image (or preset/defaults) now works. The maps are 65-stop tables
  sampled from matplotlib 3.5.1 (`core/colormaps.py`, pure Python, interpolated to 256 entries, unit-tested);
  `utils/color_tables.py` creates the `vtkMRMLColorTableNode` on first use and reuses it; `GenericSpecimen._resolve_color_node`
  tries the built-ins before Slicer's own tables. Both names are in the Config Editor's Color table dropdown. Two new files
  are listed in `CMakeLists.txt`.
- **Transparency below/above a threshold:** not part of the colour map. Use the image's existing Advanced -> *Threshold*
  (with *Apply*): values outside the range are transparent. Both maps start (almost) black at the low end.
- **Open:** a user-defined colour table in the config (custom stops) is not built; say if `gnuplot2`/`inferno` are not enough.

## [x] Batch export: confirmation; progress bar for loading and batch export

- **Status:** done in code; **not verified in Slicer** (repainting during long jobs).
- **Confirmation:** *Batch export* now asks first - "Export N finished specimen(s)? Will produce: segment label maps, markups,
  segment statistics ... can take a long time" (default answer No). With no finished specimen no question is asked; the exporter
  explains that, as before (`onBtnBatchExport` in `gui/specimen_actions.py`).
- **Progress bar** (a `QProgressBar` at the very bottom of the module, hidden until used; `ProgressReporter` / `NullProgress` in
  `utils/slicer_ui.py`):
  - loading a specimen: one step per configured image, plus segmentation, markups and the workspace setup, text "Loading <label>: ...";
  - batch export: one step per finished specimen, plus one for writing the report files, text "Batch export: <label>".
  `GenericSpecimen.load(progress)`, `GenericSpecimenManagerLogic.load_specimen(key, progress)` and `BatchProcessor(logic, progress)` /
  `batch_exporter(logic, progress)` take the reporter; without one nothing is shown (console use).
- **Limits:** the work runs on the GUI thread, so the bar only moves between steps (one big image load = one long step), and Qt is told
  to repaint with user input excluded, so clicking elsewhere cannot start a second job meanwhile. Initialize Study has no bar yet.

## [x] Reloading a config / re-initializing the study asks about closing the active specimen

- **Status:** done in code; **not verified in Slicer**.
- **Problem:** loading another config into the module (browse, or the Config Editor's "Reload this config in the active module?")
  did not ask anything while a specimen was open, and Initialize Study only asked "Save ... before continuing?" without saying that the
  specimen would be closed and the session lost.
- **Fix:** `_confirmCloseActiveSpecimen(action)` in `gui/study_setup.py`, used by both: if a specimen is open it says plainly that the
  action CLOSES it ("Specimen 'X' is open. Loading another config closes it - the open session and any unsaved work are lost") and
  offers **Save and close** (saves the specimen and the database CSV, then closes) / **Close without saving** / **Cancel** (the default).
  Cancel changes nothing (for a config load, nothing is touched before the question). After closing, the specimen buttons, labels and
  on-screen annotation are refreshed.
- **Note:** after a config load the specimen list still comes from the previous Initialize Study; press **Initialize Study** again to
  rebuild it with the new config (unchanged behaviour).

## [x] Bugfix: Initialize Study did not re-read the config

- **Status:** done in code; **not verified in Slicer**.
- **Problem:** `onBtnInitializeStudy` read the config file only when no config was loaded yet (`if self.logic.cfg is None`), so a
  config edited and saved afterwards was never picked up by "re-initialize" - the old settings stayed in effect.
- **Fix:** Initialize Study now always re-reads the config file (`_reloadConfigKeepingPathEdits` in `gui/study_setup.py`). The
  Database/Preseg CSV path fields are refreshed from the new config only where they still hold the previous config's value; a path
  typed or browsed by hand is kept. If no config path is set and none is loaded, it asks for one as before.
- Related: the active specimen is closed (with the question added earlier today) before the config is re-read.

- **Batch export with a specimen open:** `[BatchProcessor] please close the active specimen before running a batch export.` was only a log line.
  `onBtnBatchExport` now first runs `_confirmCloseActiveSpecimen("Batch export")` - the same dialog as for re-initializing (Save and close /
  Close without saving / Cancel) - and only then asks for the export confirmation. The log line stays for console use.
