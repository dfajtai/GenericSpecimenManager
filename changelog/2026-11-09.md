## [x] Segment visibility checkbox

- **Status:** done in code, **not verified in Slicer** (`vtkMRMLSegmentationDisplayNode.SetSegmentVisibility`, `vtkSegmentation.GetSegmentIdBySegmentName`).
- **Interpretation:** "a visible checkbox for the segments" = an initial-visibility setting per segment in the config, edited with a checkbox
  in the Config Editor (not a live show/hide control in the main module - say if that was meant).
- `core/config_model.py`: `SegmentConfig.visible` (None = leave Slicer's setting, False = hidden, True = shown); merges with `defaults.segment`.
- `GenericSpecimen._apply_segment_visibility()`: after the segmentation is loaded or built, every segment with `visible` set is shown or
  hidden through the segmentation's display node, matched by NAME. **Only for a segmentation built from scratch** (no saved
  `segment.seg.nrrd` yet; changed on request the same day): an existing segmentation is loaded as it is, the config's `visible` is not applied
  to it. A name that is not in the segmentation is logged as a warning. The data is not touched.
- Config Editor, Segmentation tab: new **Visible** column (ticked by default); only `visible: false` is written, so existing configs do
  not change. Defaults-level `visible` is not editable in the form (the Defaults tab is raw JSON).
- Docs: `docs/config-reference.md`, Config Editor cheat sheet, `CHANGELOG.md`.
- **Open:** whether Slicer keeps a segment's visibility in a saved `segment.seg.nrrd` (if not, a reloaded segmentation shows every segment again).

## [x] Bugfix: relative study root resolved wrongly (`etc/etc/...`)

- **Status:** done in code; the user's case (Linux, relative config path) is reproduced only as a unit test, not in Slicer.
- **Bug:** with a relative config path (e.g. `etc/config.json`) the study folder stayed relative, and the CSV / image paths joined onto
  it doubled the folder (`./etc/etc/database.csv`).
- **Fix:** `core/config_model._study_dir()` always returns an absolute study folder (config folder via `os.path.abspath`, a relative
  `study_dir` resolved against it). Test `StudyDirTest.test_a_relative_config_folder_still_gives_an_absolute_study_dir`.

## [x] Editable intensity range per brush effect (Paint / Erase)

- **Status:** done in code, **not verified in Slicer**. Implements the plan of 2026-11-05.
- **Config:** `segment_editor.editable_intensity_range: {"Paint": {"min": -50, "max": 100}, "Erase": {"min": -1024, "max": -60}}`
  (`core/config_model.IntensityRange`, `SegmentEditorConfig.editable_intensity_range`). Effects offered in the Config Editor: `INTENSITY_RANGE_EFFECTS`
  in `definitions.py` (Paint, Erase); the config itself accepts any effect name.
- **Config Editor:** Segment editor tab, group *Editable intensity range* (Min / Max per effect; both empty = not set).
- **How:** Slicer has one range per editor node (`SourceVolumeIntensityMask` + `SourceVolumeIntensityMaskRange`), shared by all effects, so
  `SourceVolumeLayerKeeper` rewrites it when `ActiveEffectName` changes (`applyIntensityRange`), also at start and when the source volume
  changes. Written on the node, not through the effect object. An end left out is taken from the source volume's scalar range; with no
  source volume and an end missing it is skipped with a warning. Other effects (Threshold ...) leave the last range as it is.
- **To check in Slicer:** that the *Editable intensity range* checkbox / slider of the Segment Editor follows the written values, and that
  switching Paint <-> Erase switches them. Log line: `[SegmentEditor] editable intensity range for <effect>: a .. b`.
- **Open:** whether unlisted effects should switch the range off (now: they keep the last one).

## [x] Config Editor: relative study root, CSV parsing, quick add

- **Status:** done in code, **not verified in Slicer** (Qt code; no unit test possible here).
- **Cause of `etc/etc/...`:** the editor saved `study_dir` = the folder part of the preseg path (`"etc"` for `etc/img_paths.csv`), then the
  module resolved `etc/img_paths.csv` under `<config>/etc`. Also, the editor itself resolved relative CSV paths against the process's
  current directory (`"."`), so *Show CSV columns* and the quick-add list read the wrong place - and the config's own folder was not
  even known while a config was being loaded.
- `general_tab`: `_configFolder()` (Output config.json field, else the loaded file) and `_studyRoot()` (Study dir - relative = under the config
  folder; else the preseg's folder if that path is absolute; else the config folder). `_resolveCsvPath`, the Browse "relative to" roots of
  the preseg / database fields and `_populateGeneral` use it. Saving writes `study_dir` only when typed or derivable from an absolute
  preseg path; otherwise the key is left out (module default = the config's folder).
- `dialog._loadFromFile` sets the config's path before populating the form.
- Images tab, *Quick add from preseg columns...*: reads the preseg CSV header at that moment (no dependency on the General tab having
  parsed it), and says which path it tried when the file cannot be read.
- Configs saved by older editor versions with `study_dir: "etc"` still mean `<config>/etc` - remove or fix that key by hand.

## [x] Auto-parse of the preseg CSV with relative paths

- **Status:** done in code, not verified in Slicer (Qt code).
- The preseg header was read only when the preseg field itself was edited / browsed, so with a relative path a later change of the Study

  list stale or empty. New `_reparsePreseg()` runs on Study dir (typed or browsed) and on the Output config.json field (typed or browsed);
